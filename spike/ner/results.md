# 中文 NER 技术选型实测结果（spike/ner）

> 目标：为"本地中文文档脱敏工具"验证中文人名/机构名/简称自动识别方案的可用性与真实水平。
> 检测层设计：正则规则 → 词典精确匹配 → 上下文规则 → 中文 NER 模型（可选增强，ONNX INT8 量化 CPU 部署）。
> 本 spike 重点验证 **NER 层选型** 与 **"词典兜底 NER"组合效果**。

---

## 1. 评测设置

### 1.1 语料（corpus.json）

3 段贴近真实合同/协议的中文文本，共 21 个标注实体（span 级，字符索引，end 不包含）：

| 文档 | 长度 | PER(人名) | ORG_FULL(机构全称) | ORG_SHORT(机构简称) |
|---|---|---|---|---|
| 劳动合同 | 359 字 | 张三、李四 | 北京降本增笑科技有限公司 | 降本增笑 ×2 |
| 采购合同 | 326 字 | 王五、赵六、陈七、周八 | 杭州星火信息技术股份有限公司、上海稳赢数据服务有限公司 | 星火信息 ×2、稳赢数据 ×2 |
| 保密协议 | 255 字 | 孙九、林十 | 深圳开源先锋软件有限公司 | 开源先锋 ×3 |
| **合计** | 940 字 | **8** | **4** | **9** |

语料同时包含地址/手机号/身份证号等结构化 PII（未标注，属于正则层范围）。
标注规则：简称只标注独立出现处（不含全称内部的子串）；如 "北京降本增笑科技有限公司（以下简称"降本增笑"）" 中，全称与括号内简称分别标注。

### 1.2 指标

- **span 级 P/R/F1**（按类型独立，完全匹配才算命中），并额外计算 **ORG_ALL**（ORG_FULL ∪ ORG_SHORT 合并后评测）——因为脱敏时全称/简称都会打码，产品只需"识别出是机构"。
- 耗时：3 篇文档逐一推理的平均值（CPU，Apple Silicon）；ONNX 另做 10 轮公平计时。

### 1.3 环境

- macOS（Apple Silicon），Python 3.11.15（venv 内，未全局安装）
- 网络：huggingface.co 直连失败、hf-mirror.com / modelscope / github 可达 → 全部模型走 hf-mirror 手动下载
- 版本坑：LTP 4.2.14 与 transformers 5.x 不兼容（`batch_encode_plus`/`use_auth_token` 被移除）→ 需锁 `transformers==4.46.3`、`huggingface_hub==0.25.2`

## 3. 各路线详情

### 3.1 路线 a：jieba + 规则基线（可用，作为第 2/3 层补充）

- 公司后缀启发式（"有限公司/股份有限公司"等 12 类后缀 + 向前扩展）对**机构全称 100% 命中**、零误报。
- 姓氏启发式人名：召回 100% 但误报 22 个（"劳动"、"平等"、"合同"、"公司"等以姓开头的高频词），P 仅 0.267。
- **简称识别为 0**（无规则可循），ORG_ALL 仅 0.471。
- 结论：规则基线只适合做**全称识别**的强启发式（可并入词典层之前），不足以独立承担人名/简称。

### 3.2 路线 d：词典 + 上下文（可用，简称问题的工程正解）

实现：种子词典（公司全称）最长匹配 → ORG_FULL 100%；扫描 "（以下简称"X"）" 模式**学习全称→简称映射**，再用映射匹配正文 → ORG_SHORT 9/9 全命中；全流程 <0.1ms/文。
- 第一次尝试（朴素"去地名+去后缀"推导简称）失败：推导出"星火信息技术"≠ 真实简称"星火信息"——**简称是商业约定，不可靠自动推导**，必须靠词典/上下文学习。
- 该路线的 ORG 系列达到 1.0，几乎零成本。代价：只覆盖词典内与文档内定义过的机构。

### 3.3 路线 b：fastHan（不可用，模型已丢失）

- `pip install fastHan==1.8` 可装（py3.11 需配 fastNLP 0.7、transformers 4.x）。
- **模型参数已丢失**：官方 README 明确声明"由于服务器故障导致 fastHan 模型参数丢失，目前暂停服务"；原下载服务器 download.fastnlp.top 已停机（实测连不上）；HF 上的 `fdugzc/fasthan_base` 仓库返回"Invalid username or password"（私有/不存在）。
- 结论：**当前时点无法获取 fastHan 权重，路线不可用**。若日后官方恢复模型分发，可复用本 spike 的评测流程复测。

### 3.4 路线 c：LTP（可用但合同场景质量差）

- 包 `ltp==4.2.14`（MIT）+ 模型 LTP/small（ELECTRA backbone，~179MB）可跑通。
- 人名 F1=0.857 尚可；**机构识别几乎不可用**（ORG_ALL F1=0.056，22 个误报，全称常被切碎、简称不识别）。
- 原因：LTP 预训练数据偏新闻/通用语料，合同领域的"编号/地址/金额/普通名词"触发大量机构误报。
- 结论：**不建议作为产品的 NER 主力**；若选用，必须做领域微调，否则误报带来的脱敏误伤不可接受。

### 3.5 路线 e：ONNX BERT NER（推荐，选型胜出）

- 模型：`protectai/gyr66-bert-base-chinese-finetuned-ner-onnx`（BERT-base，CLUENER 标签集，**Apache-2.0** 可商用），FP32 407MB / 动态 INT8 102MB，onnxruntime CPU 推理。
- 标签集对脱敏工具非常对口：`name / company / organization / address / mobile / email / government / QQ / vx / position ...`——除人名机构外，手机号/邮箱/QQ/微信号等都能识别（可并入正则层的补充）。
- 实测：**人名 8/8（F1=1.0）**；机构 ORG_ALL F1=0.750（FP32，漏 4 处括号内简称）；对"简称"能识别为机构但**不区分全称/简称**（评测分类型时表现为 ORG_FULL 误报 / ORG_SHORT 漏报，产品视角无碍）。
- 动态 INT8 量化：体积 -75%（407→102MB），但 **CPU 推理无加速**（70.8ms vs 72.7ms/文，10 轮均值）——动态量化主要压缩权重，BERT 短文本 CPU 推理瓶颈不在权重带宽；且 INT8 后模型更保守（少标），单模型 ORG_ALL R 从 .692 降到 .462。

### 3.6 组合方案 f：NER + 词典兜底（产品推荐形态）

- ONNX+词典：PER **1.0**、ORG_ALL **0.929**（FP32）/ **0.963**（INT8），召回 100%，仅 1~2 个误报。
- LTP+词典：ORG_ALL 0.542，被 LTP 的 22 个机构误报拖累。
- 结论：**"词典兜底 NER" 组合成立**——NER 负责人名与未登录机构，词典+上下文负责简称，两者互补后达到产品可用水平。

## 4. 选型建议

### 4.1 产品默认层组合（推荐）

```
文本 → ① 正则规则（手机/身份证/银行卡/邮箱/地址等结构化 PII，先脱敏）
     → ② 词典精确匹配（公司全称/简称、人名黑名单、专有名词，最长匹配）
     → ③ 上下文规则（“（以下简称 X）”学习简称映射；职务/联系人/法定代表人的“：X”上下文）
     → ④ ONNX 中文 NER（可选增强，默认开启，脱敏未登录人名/机构）
```
- ②③ 层对"公司简称"的工程对策 = **词典关联（全称→简称）+ 文档内"以下简称"上下文学习**，实测简称 F1 可达 1.0；不要用"去地名去后缀"自动推导简称（实测推导结果与真实简称不符）。
- NER 层的 ORG 输出不再区分全称/简称，统一按"机构"脱敏（结合②③层保证简称不漏）。

### 4.2 NER 模型选型

| 候选 | 结论 |
|---|---|
| **ONNX BERT NER（gyr66，CLUENER，Apache-2.0）** | ✅ **选用**。人名 F1=1.0、机构 ORG_ALL 0.75；许可安全；有现成 ONNX 可直接 CPU 部署；标签集还覆盖手机/邮箱/QQ/微信 |
| LTP（small/tiny） | ❌ 不建议。合同场景机构误报率极高（ORG_ALL F1≈0.06），需领域微调成本高 |
| fastHan | ❌ 当前不可用（模型参数丢失）。若官方恢复分发可复测（评测脚本已就绪） |

### 4.3 量化方式建议

- **部署用动态 INT8**（102MB）：体积与内存友好，精度几乎无损（组合 F1 0.929→0.963）；但**不要指望它加速 CPU 推理**（实测无加速）。
- 追求更快推理的后续路线：静态量化（QDQ + 校准数据）、蒸馏到 ELECTRA/ALBERT 小模型、或换 onnxruntime 的更高优化（如 `EP`/int8 MKL 内核，需 Linux x86 验证）。
- 额外收益：该模型在 macOS 单条 300~360 字合同文本推理 43~80ms，对"按文档脱敏"的产品是够用的（文档级脱敏通常可接受秒级以内）。

### 4.4 对产品的影响（要点）

1. **NER 层可选增强的定位成立**：纯规则+词典基线（a+d 合并）已能拿到 PER 缺失、ORG 100%（限词典/上下文覆盖范围）；ONNX NER 主要补充**未登录人名（100%）**与**未登录机构（ORG_ALL 0.75）**，组合后 PER 1.0 / ORG_ALL 0.93+。
2. **简称识别难点有确定性解法**：词典关联 + "以下简称"上下文学习（F1 1.0），不依赖 NER。
3. **误报治理**：NER 会把地址/编号/普通名词标为机构——产品需在 NER 层后加**白名单/置信度过滤**（本 spike 未验证，建议用 CLUENER 测试集或扩充合同语料做阈值标定）；LTP 类模型在该场景误报过多，属于红线。
4. **许可合规**：全链路 MIT/Apache-2.0（jieba MIT、LTP MIT、ONNX 模型 Apache-2.0、onnxruntime MIT），满足商用约束。fastHan 若日后恢复需再核对其实际 LICENSE 文件（1.8/2.0 的 PyPI 声明为 Apache License）。

## 5. 局限性与后续验证

- 语料仅 3 篇合同（21 个实体），统计效力有限；建议扩到 30~50 篇真实合同再定最终阈值。
- span 级完全匹配是严格口径；产品若允许"重叠/部分命中"（如 NER 识别出"星火信息技术股份"也应打码），实际 F1 会更高。
- 未验证：超 512 token 长文档的滑窗策略、NER 置信度阈值、静态量化精度、以及 onnxruntime 在 Linux/Windows CPU 上的 int8 内核收益。
- 复现：`bench.py` 支持 `--fasthan/--ltp/--onnx/--all`，模型已缓存在 `.ltp_cache/` 与 `.onnx_cache/`（走 hf-mirror 下载，见文件内说明）。
